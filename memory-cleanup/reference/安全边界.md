# 安全边界（机制层理由）

> 只下发禁令、不给理由，等于把"被遵守"寄托在执行者的服从上；执行者换了、或者他手上正好有个更省事的方案，禁令就失效了。
> 所以本文每条禁令都写到**机制层**：不是"这样做更好"，而是"另一种做法在机制上会错在哪、错多大"。

## 零、这份边界在防什么

- **防误伤**：让"杀错进程"在机制上难以发生，而不是靠执行时小心。
- **防误判**：让"清理成功"成为可证伪的结论，而不是一次读数加一句感觉。
- **防不可逆**：让每一步都能回退，直到用户明确确认。

**七条禁令一览**（理由写在正文各节；这里是速查表，不是替代）：

| # | 禁令 | 机制层理由的关键词 | 详见 |
|---|---|---|---|
| 1 | 只按路径终止自动化浏览器 | 独立 `--user-data-dir` 写在命令行里，路径是唯一稳定标识 | §一 |
| 2 | 绝不按内存大小挑进程 | RSS 是资源指标、不是状态指标；按大小杀＝优先杀有状态进程 | §二 |
| 3 | 有状态进程只读计数 | 未发送消息／未保存文档／登录会话退出即不可恢复 | §三 |
| 4 | 先确认再动手 | 归属证据 ≠ 任务状态证据；终止在跑实例会造成半提交 | §四 |
| 5 | 不直接清空废纸篓 | 不可逆；两段式把删除拆成可回退搬移＋有日期终删 | §五 |
| 6 | 超龄用日期文件夹名，不用 `mtime` | `mtime` 是内容修改时间，`mv` 不改时间戳，按它判会提前删 | §五 |
| 7 | 失败如实报，不重试不硬删 | 失败码指向不同原因；硬删绕过权限边界、误删范围失控 | §七 |

**判据性质**：本技能对"某进程属于哪个程序"的判断，只依据本机命令行与路径。**这些均为本地证据，不构成对该进程用途或安全性的授权依据**——路径能证明"它是谁启动的"，不能证明"它此刻在做什么、用户还需不需要它"。两者的差额必须由用户补上，这就是下面第四节的来历。

## 一、只按路径杀：为什么路径能替代"名字、图标、大小"

**禁令**：只终止命令行中含 agent 浏览器缓存目录（config 的 `agent_browser_path`）的 Chrome 进程。

**机制事实**

1. 自动化浏览器不是"用户那个 Chrome"。它以独立的 `--user-data-dir` 启动，这个参数是启动时写死的，**必然出现在进程命令行里**，且 `pgrep -f` 读的正是整条命令行。
2. 用户手动打开的 Chrome 用默认 profile 目录，与应用 bundle 路径绑定；两者不共享同一个 user-data-dir。**所以"命令行含该路径"与"是自动化实例"在机制上等价**，不是相似、不是概率。
3. 进程名不可靠（都叫 `Google Chrome` 或 `Chromium`）、图标不可靠（同一个 app bundle）、占用大小不可靠（同一实例内存随页面数浮动）。**三条都不可靠时，只有启动参数里的路径是唯一稳定标识。**

**为什么这比"人工挑进程"可靠**：人工挑依赖列表的显示完整性，而 `pgrep` 读到的是内核里的 argv，不经过任何界面的省略号。

**失效条件（必须知道）**：若某自动化工具启动浏览器时**不带 `--user-data-dir`**，路径判据当场失效。此时的正确动作是**停手并告知用户"该工具无法用路径定位"**，而不是退回去用大小或名字判。判据失效就换判据的设计，不是换判据的松紧。

## 二、绝不按内存大小杀：为什么这条不是"保守"，而是"方向性错误"

**禁令**：任何情况下不按 RSS／内存占用排序挑进程终止。

**机制事实**

1. **RSS 是资源指标，不是状态指标。** 它回答"用了多少内存"，不回答"退掉会不会丢东西"。用 A 的判据去回答 B 的问题，错的不是阈值高低。
2. **占用大与"有价值的状态多"通常是正相关，不是负相关。** 微信占内存多，是因为消息缓存、会话、未发送草稿都在里面；办公文档编辑器占内存多，是因为整份文档、撤销历史在内存里；用户浏览器占内存多，是因为开了几十个标签和登录会话。**"谁大杀谁"的排序结果，恰好等于"优先杀掉状态最重的进程"**——方向反了，而且反得很稳定。
3. **终止动作不可逆**：进程退出后，未落盘的东西没有回收站。回收站能救"删掉的文件"，救不了"没保存的文档"。
4. **"内存压力大所以要腾内存"这个推理本身不成立**：macOS 的内存管理会把可回收页（文件缓存、干净页）优先回收，真正把内存逼到 swap 的是**常驻且不可回收**的部分。杀一个状态重的进程能腾出内存，代价是那部分状态；收益与代价不在同一个维度上，不能相减。

**那用什么替代**：**只读计数 + 用户点名**。技能给数字（微信类进程 N 个、上限 M），用户决定动不动、动哪个。技能没有"用户此刻还需要什么"的信息渠道，就不该替用户做这个决定。

**失效条件**：无。问题不在阈值设多少，而在判据类型错了——把阈值调到多高都还是同一个错误。

## 三、有状态进程只做只读巡检：名单与理由

**名单**按角色识别、不按型号，含同类变体：即时通讯（微信、企业微信等）、办公套件（文字／表格／演示）、用户浏览器、笔记与知识库工具、IDE 与终端复用器。**尤须留意含未保存文档的办公套件**，它属于"一退就丢"的那一类。

**机制理由**：这些进程的内存里驻留着**无法从磁盘恢复**的状态——未发送的消息队列、编辑缓冲区与撤销历史、登录会话与二次验证状态、未提交的编辑。区别不在"重要不重要"，而在"退出后能不能原样回来"。能回来的（浏览器标签可恢复、缓存可再生）与不能回来的（未保存文档）混在一起，所以默认全部不动。

**提示话术模板**（只建议，不动手）：

> 微信类进程当前 N 个，超过上限 M。建议你退出微信重开（进程数会回落，内存也会降）；这一步我不替你动手——里面有你的会话和未发送消息。

## 四、先确认再动手：归属证据 ≠ 任务状态证据

**禁令**：执行清理前必须由用户确认"当前没有正在跑的上传 / 浏览 / 抓取任务"。

**机制理由**

1. 路径判据只证明"这个进程是自动化浏览器"。它**不包含**"有没有任务正在使用它"这一个比特的信息。
2. 正在上传的实例被终止，可能停在**半提交**状态：远端已收到部分分片、本地会话已断。这种状态比"没传"更难收拾，且技能无从判断该重传还是回滚。
3. **两条证据不能互相顶替**：知道它是谁的进程，和知道它此刻在做什么，是两件事。缺后一件就必须问，不能拿前一件凑。

**操作序列**（缺一步即不动手）：读数 → 报"当前 N 个实例" → 问"现在有任务在跑吗" → 用户答"没有" → 才执行 → 验证 → 汇报。用户答"有"或含糊，本轮只报告。

## 五、回收站两段式：为什么不能直接清空、为什么不能用 mtime

**禁令一**：绝不直接清空 `~/.Trash`；最终删除必须经"归档区停留 N 天 + 用户确认"。

**机制理由**：清空是不可逆操作，且 Finder 的"清倒废纸篓"没有任何确认以外的保护。两段式把一次不可逆动作拆成**一次可回退的搬移**（`mv` 到 `~/.Trash.aged/<日期>/`，随时能搬回）和**一次有日期的最终删除**。中间这段时间就是后悔期，它的长度是可配置的（`trash_aged_days`，归档区停留 N 天、受控后悔期＝N 天），而不是零；回收站侧停留时长本技能不测量，因此不承诺两段之和。

**禁令二**：超龄判据用**日期文件夹名**，不用文件 `mtime`。

**机制理由**

1. `mtime` 是**内容最后修改时间**，与"什么时候被删"没有任何关系。一个 2019 年改过、今天刚删的文件，`mtime` 还是 2019 年——按 `mtime` 判超龄，它会在被删的**当天**就被永久删除，后悔期为零。这不是"偶尔误杀"，是**判据本身在定义上就错**。
2. `mv` 在同一卷内**不改变文件的任何时间戳**（只改目录项），所以搬进归档区后 `mtime` 依然是旧的。**用 `mtime` 判"进归档区多久了"必然错**，错的方向是"提前删"。
3. 日期文件夹名 `2026-11-16` 由搬入当天的 `date +%F` 生成，**是这套流程里唯一显式记录"删除时间"的字段**，且用户肉眼可核、可手工纠正。
4. 第二段用 `find "$AGED" -maxdepth 1 -type d -name "????-??-??" -mtime +N`：这里 `mtime` 判的是**文件夹**——文件夹的 `mtime` 在每次往里搬东西时更新，因此它**不早于**该文件夹名的日期。用它做粗筛只会让删除**延后**，不会提前。**判据主体是文件夹名，`mtime` 只是"够不够天数"的保守粗筛**，两者的关系是"与"，不是"或"。

**用户可感知的差别**：直接清空＝一次操作、零后悔期；两段式＝两次触碰、后悔期可配置、每一步都能说清"什么时候进来的"。

## 六、只碰 `~/.Trash` 与 `~/.Trash.aged`

**机制理由**：外接卷的回收站是 `/.Trashes/<uid>/`，由系统按卷管理，权限与属主跟启动盘不同。跨卷 `mv` 在机制上等于"复制 + 删除原文件"——大文件会慢，中途失败会留下**两处都不完整**的中间态，且失败后原文件可能已被删掉。把外部卷并进同一个流程，等于把"可回退"换成"可能两边都没有"。

**失效条件**：用户明确要求清某个外接卷的回收站——那时按卷单独处理、单独确认，不并进本流程。

## 七、`.DS_Store` 不动，失败不重试、不硬删

**`.DS_Store`**：Finder 的目录视图元数据。删掉它不影响文件，但会让目录的排序、图标位置、视图方式复原——属**与任务无关的副作用**，收益为零而副作用确定。

**失败不重试**：`mv` / 删除的失败码指向不同原因（权限、被占用、跨卷、目标不存在）。**重试会把一个可诊断的错误变成一堆不可诊断的噪音**；`sudo` 硬删则绕过权限边界，让误删范围重新变得不可控。正确做法是如实报路径与错误，把决定权交回用户。

## 八、执行前自查表（五问，任一项答不出就不动手）

1. `agent_browser_path` 设了没有？为空是否应当跳过（默认跳过）？
2. 用户是否明确说过"现在没有任务在跑"？（含含糊的"应该没有"＝没有）
3. 本次要终止的进程，其命令行是否**逐字**含该路径？
4. 回收站流程是否只碰两段目录、只碰日期命名文件夹、删前报过路径与体积？
5. 报告里是否给出**前后两次数值**，而不是只有一次"清理完成"？

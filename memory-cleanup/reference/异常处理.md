# 异常处理与口径

> 原则：**任何异常都回退到"用预设值继续跑 + 报告里说一句"，绝不静默改判据、绝不中止到没有结论。**
> 唯一允许中止的情形是 `SKILL_DIR` 未设——因为猜错目录会读到别人的 config，甚至往别人目录里写模板。

## 一、config 损坏

**结论先行**：坏了不中断——整体回退预设值，报告里说一句，修好下次生效。下面是怎么判、怎么修。

**检测**

```bash
jq -e . "$CONFIG" >/dev/null 2>&1 && echo OK || echo 损坏     # 有 jq
tr -d '[:space:]' <"$CONFIG" | grep -q '^{.*}$'                # 无 jq：粗判首尾花括号
```

**常见形态**共五类：语法错（截断、少逗号、多逗号）、空文件（0 字节）、首尾像 JSON 但中间坏、写成带注释的 JSON5、BOM 开头。这五类都会被 jq 判为损坏。

**处置**：**整体回退预设值**（四项参数全部取默认），报告里加一句"config.json 解析失败，已整体回退预设值继续运行；修好后下次生效"。**不中断流程，不猜坏在哪一行。**

**为什么不"尽量抢救能读的字段"**：坏文件的字段值同样可能是错的（例如截断后 `"swap_warn_mb": 1` 恰好语法上像个合法数字）。**同一个文件既然已不可信，就不能挑着信它**——整体回退是可解释的，挑着读是不可解释的。

**修复路径**

```bash
cp "$CONFIG" "$CONFIG.bak-$(date +%Y%m%d)"   # 先留档，不删
# 然后按模板重建（见 SKILL.md 第四节的生成块），或手工修好后再跑一次
```

修没修好，看下一轮报告第一行的三个数值是否等于你写进去的值。

## 二、单个键缺失 / 类型错 / 越界

| 情形 | 判据 | 处置 |
|---|---|---|
| 键不存在 | `mc_get` 返回空 | 该键用预设值，**不提示**（视为有意留空） |
| 值是小数、布尔、对象 | 值不符合"非负整数" | 该键回退预设 + 提示 |
| 越界 | `swap_warn_mb` 不在 4096~32768；`wechat_max_procs` 不在 10~50；`trash_aged_days` 不在 3~30 | 该键回退预设 + 提示可调范围 |
| 数字写成字符串（`"8192"`） | 可解析为整数 | **照常采用**，不视为错误（手写 config 常见） |
| 存在废弃键 `trash_keep_days` | 该键自 v1.0.2 起并入 `trash_aged_days` | **忽略该键**，报告加一句"提示：检测到已废弃键 `trash_keep_days`，已忽略——两段天数由 `trash_aged_days` 统一管理"；取值不受影响 |

**为什么单键回退而不是整体回退**：损坏文件是"文件不可信"，越界是"这一个值不可采信"——其余键没有问题，没有必要连坐。报告里逐项写出哪几个键被回退，用户能一眼定位。

**废弃键的检测口径（两条解析路径必须同结论）**：有 `jq` 时用 `jq -e 'has("trash_keep_days")'`；无 `jq` 时不能用 `grep -q '"trash_keep_days"'`——键名若出现在**字符串值**里（如注释文本提到它）会误报。降级路径改用键位 ERE：

```bash
grep -qE '(^|[{,])[[:space:]]*"trash_keep_days"[[:space:]]*:' "$CONFIG"
```

要求键名前是行首、`{` 或 `,`，且键后紧跟 `:`。实跑对照四种情形（多行有键／单行有键／键名在字符串值里／无键），两条路径结论一致。

## 三、`jq` 不存在时的降级解析

```bash
sed -n 's/.*"'"$1"'"[[:space:]]*:[[:space:]]*"\{0,1\}\([^",}[:space:]]*\)"\{0,1\}.*/\1/p' "$CONFIG" | head -1
```

**能处理**：平铺的一层对象、数字与带引号的字符串、键值间任意空格。

**不能处理（已知局限，必须在报告里承认）**

1. **嵌套与数组**：`{"trash": {"aged_days": 7}}` 取不到。本版 config 刻意保持平铺，就是为了让降级路径可用。
2. **值里含逗号或右花括号**：会被截断。路径里带逗号时降级解析会读错——此时请装 `jq`，或把该键留空走"检测建议"路径。
3. **重复键**：只取第一处。
4. **损坏判定只是粗判**：`^{.*}$` 通过不代表语义合法（例如 `{"a":}`）。降级模式下若某键取不到值，走"预设 + 不提示"，不会误用坏值。

**两种解析路径必须给出同一结果**：换机器（有的 macOS 自带 jq、有的没有）不该导致阈值变化。自测方法：同一份 config 分别在 `PATH` 含 jq 与不含 jq 两种环境下跑一遍，第一行三个数应完全一致。

## 四、`pgrep` 口径（本技能最容易出错的地方）

### 4.1 macOS 的 `pgrep` 没有 `-c`

```
usage: pgrep [-Lfilnoqvx] [-d delim] [-F pidfile] [-G gid]
             [-P ppid] [-U uid] [-g pgrp] [-t tty] [-u euid]
             pattern ...
```

`-c`（输出计数）是 Linux procps 版才有的选项。**照抄 Linux 写法会直接报错退出**，在脚本里表现为"计数那一行没输出"，容易被误读成"0 个实例"。统一写法：

```bash
n=$(pgrep -f "$PATTERN" 2>/dev/null | wc -l | tr -d ' ')
```

### 4.2 `-f` 会命中执行者自己的命令行

`-f` 匹配的是**整条命令行**。如果模式串直接写在命令里，麻烦就来了。执行这条命令的 shell，argv 里恰好含同一串（例：`pgrep -f "/Applications/WeChat.app/"`）。于是它自己也被算进去，**计数多 1**。用变量拼接可避开（执行者的 argv 里是 `$P` 不是展开后的值）：

```bash
P="WeChat.app"; pgrep -f "/Applications/$P/"
```

是否多算 1 取决于调用方式（写进脚本文件、heredoc、还是 `bash -c` 直传），**同一台机上两种写法都可能出现**，所以统一用变量拼接，不去赌。

### 4.3 crashpad 子进程：算不算

`crashpad_handler` 的 argv 里带同一路径，会被同一个模式命中。**关键不在算不算，在两条口径必须同源**。清理用 `pkill -f 路径`，会连 crashpad 一起终止。计数若排除 crashpad，就会出现"清理后计数已 0、但进程还在"的假阴性，验收线当场失效。

本版统一口径：**计数含 crashpad**，与清理口径一致；报告里如需区分，另给一行"其中 crashpad N 个"，但不改变主计数。

### 4.4 计数为 0 不是错误

`pgrep` 无匹配时退出码为 1，`wc -l` 仍输出 `0`。**不要把退出码 1 当成失败分支**（在 `set -e` 的脚本里会让整个流程中止）。同理，`pkill` 无匹配也返回 1。

### 4.5 微信类的计数口径

按 app bundle 路径匹配，两产品分列后相加，**含 Helper / GPU / 网络子进程**——内存是按子进程摊的，只数主进程会系统性低估：

```bash
P="WeChat.app";       W1=$(pgrep -f "/Applications/$P/" 2>/dev/null | wc -l | tr -d ' ')
Q="企业微信.app";     W2=$(pgrep -f "/Applications/$Q/" 2>/dev/null | wc -l | tr -d ' ')
WX=$(( W1 + W2 ))
```

装在非 `/Applications` 位置的，改路径前缀即可（判据是"bundle 路径"，不是"产品名"）。`pgrep -f -i "WeChat"` 这种模糊写法不要用：它会命中带 `WeChat/…` user-agent 的企业微信子进程，两产品的数就混了。

### 4.6 空模式串：报错会被误读成"0 个"

macOS 实测：

```
$ pgrep -f ""
pgrep: Cannot compile regular expression `' (empty (sub)expression)
$ echo $?
2
```

**没有输出、退出码 2**。若脚本写成 `n=$(pgrep -f "$P" | wc -l)`，得到的是 `0`——看上去"没有实例"，实际是"根本没查"。清理后的验证若踩这一脚，**验收永远显示 0，且不会报错**，是最难发现的一类假阴性。

对照：`pgrep -f "."`（任意一个字符）会命中全部进程（实测 700+ 个）。**模式串的"空"与"任意"是两件完全不同的事。**

跨平台要小心：另一些平台的 `pgrep` 实现把空正则当作"匹配全部"。**两种平台的坏法相反，所以统一做法是先判空再执行**，不要依赖某个平台的具体行为。

## 五、`memory_pressure` 不可用

个别 macOS 版本／受限环境下 `memory_pressure` 不在或输出格式变化。降级用 `vm_stat` 估算**可用内存占比**：

```bash
vm_stat | awk '
/page size of/ { ps=$8 }
/^Pages free/ { fr=$3 } /^Pages inactive/ { ia=$3 } /^Pages speculative/ { sp=$3 }
/^Pages active/ { ac=$3 } /^Pages wired/ { wd=$4 } /^Pages occupied by compressor/ { cp=$5 }
END { gsub(/\./,"",fr); gsub(/\./,"",ia); gsub(/\./,"",sp); gsub(/\./,"",ac); gsub(/\./,"",wd); gsub(/\./,"",cp);
      tot=fr+ia+sp+ac+wd+cp; if (tot>0) printf "%d\n", (fr+ia+sp)*100/tot }'
```

**必须承认的差别**：这里算的是"可用页 / 全部页"，与 `memory_pressure` 报的 free percentage 是两套口径。**两者数值不可互换**，同一时刻实测可差十几个到二十几个点。所以报告里要标"估算值"，且**只与同口径的另一次读数做前后对比**，不拿去和 `memory_pressure` 的读数比大小。跨口径比较得出的"内存释放了 X%"是假数。

## 六、`sysctl vm.swapusage` 不可用

跳过 swap 判据，报告里写"swap 读数不可用，本轮未做 swap 判据"，**不要用 `ps` 或估算替代**——猜出来的 swap 数会污染前后对比。

## 七、技能目录只读 / 不可写

首次运行需要生成 config 时，若目录不可写：**不写、不报错、不中止**，仅用预设值继续，报告里加一句"技能目录不可写，未生成 config.json；需要固定阈值请手工放置该文件"。**不往 `/tmp` 或用户主目录找替代落点**——配置散落在多处，比没有配置更难排查。

## 八、跨卷搬移或删除失败

`mv` 到归档区、`rm -rf` 超龄文件夹失败时，**如实报路径与错误，不重试、不 `sudo` 硬删**。常见原因：目标卷是外接卷（`EXDEV`，跨卷 mv 等于复制+删除）、文件正被占用、权限不足、路径已被外部改掉。失败项要进报告，并在下一轮重新列出——**不把"没删掉"写成"已清理"**。

## 九、平台边界

本技能只对 macOS 负责。Linux 上三处不同。第一，`pgrep -c` 可用，但 `memory_pressure`／`vm.swapusage` 不存在。第二，`find -mtime` 语义相同。第三，回收站机制是 `~/.local/share/Trash`。**把这些凑到一份脚本里，等于每次运行都在赌分支**——不在本技能范围内。

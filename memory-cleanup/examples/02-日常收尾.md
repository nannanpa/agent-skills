# 场景二：日常收尾（单次任务跑完之后）

**触发语**：「收尾清理」「任务收尾」「传完了，清一下」

**前提**：`agent_browser_path` 已填好（首诊时填过）；用户刚跑完一次上传/抓取/截图任务。

## 执行要点

1. **读阈值 → 三行报告**（每轮都打，不只首次；阈值是"本次实际生效值"）。
2. **只读巡检**：重点看实例数（任务跑完常见 1~3 个残留）与微信类进程数。
3. **确认**：任务刚跑完，"没有任务在跑"通常成立，但仍要问一句——**问的是"还有下一批吗"，不是"刚才那批完了吗"**。批量任务常常紧接着跑第二批，这是本条最容易踩的坑。
4. **基线 → 清理 → 验证**。
5. **报告**：一句话结论在前（"实例清干净了，内存回来了 X 个点"），数字在后。

## 报告长什么样（示例数值为示意）

```
本次按以下阈值执行：swap 警戒 10240MB ｜ 微信上限 20 ｜ 回收站归档区 7 天（受控后悔期，回收站侧不计入） ｜ agent 路径 /Users/<you>/.agent-browser/browsers。
可调项：…
内存档位：本机 16GB，swap 线建议 10240MB，与当前值一致。

巡检：实例 3 ｜ 空闲 22% ｜ swap 已用 5980MB ｜ 微信类进程 18
清理：已终止 3 个实例，5 秒后复查 0
对比：实例 3→0 ｜ 空闲 22%→29% ｜ swap 5980→5975MB
建议：无（各项未超线）
```

## 验收对比

| 项 | 基线 | 收尾 | 判过标准 |
|---|---|---|---|
| 实例数 | 3 | 0 | 归零；不为 0 要说明是残留还是新起的 |
| 空闲 % | 22% | 29% | 上升即可；**不设绝对线**（同机相邻两分钟可差几个点，跨机不可比） |
| swap 已用 | 5980MB | 5975MB | 变化 ≤ 数十 MB 属正常；**大幅上涨**要回头查是不是还有实例在跑 |
| 建议条数 | — | ≤3 | 给太多等于没给 |

**日常收尾的判过标准比首诊松**：这里的目标是"不积压"，不是"榨出每一兆"。实例归零即达目的，内存能回来多少是副产品。

## 与首诊的区别

首诊要顺带**校准阈值**（对照内存档位给建议、决定 `agent_browser_path` 填不填）；日常收尾只执行，不改配置。**配置改动集中在首诊和"调阈值"两个场景**，日常路径上不夹改动，这样出问题时变量最少。

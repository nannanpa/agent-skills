# 场景五：调阈值（改 config 并验证生效）

**触发语**：「把 swap 警戒线调到 16384」「微信上限改成 12」「回收站压到 3 天」「改阈值」

**前提**：用户有明确目标值，或报告第三行给了"建议上调/下调"而用户采纳。

## 执行要点

1. **先确认改哪个键**：四个参数各自的可调范围不同，越界会被回退（改了等于没改，还多一条提示）。
   - `swap_warn_mb` 4096~32768
   - `wechat_max_procs` 10~50
   - `trash_aged_days` 3~30（**归档区停留天数**，即刻受控后悔期；回收站侧时长不测）
   - `agent_browser_path` 任意绝对路径，空串＝跳过清理步
2. **改前留档**（可选但推荐）：`cp config.json config.json.bak-$(date +%Y%m%d)`。
3. **只改目标键，其余键原样保留**：手工编辑时最容易连带把别的键写坏。
4. **立刻复跑一次报告**（不用等下次），确认第一行已变成新值——**改没改对，看报告不看文件**。
5. **一句话回报**："swap 警戒 10240→16384MB，已生效；本机 16GB，建议值 10240MB，你确定要上调就在下次报告里继续用 16384。"
6. **回收站天数改动要提醒受控后悔期**：取 3 → 归档区停 3 天；取 30 → 归档区停 30 天。这是归档区受控天数，不含回收站侧时长；改小之前说一句。

## 报告长什么样（示例：把 swap 线从 10240 调到 16384）

```
本次按以下阈值执行：swap 警戒 16384MB ｜ 微信上限 20 ｜ 回收站 7+7 天 ｜ agent 路径未设（已跳过）。
可调项：swap 警戒线 4096~32768MB ｜ 微信上限 10~50 ｜ 回收站归档天数 3~30 天 ｜ agent 路径填绝对路径（留空即跳过）；改 config.json 对应键，下次运行生效。
内存档位：本机 16GB，swap 线建议 10240MB（当前 16384MB），可下调。
```

**注意第三行**：档位建议不会因为用户改了值就跟着变——它按**物理内存**算。两者不一致时报告如实并列，**既不静默纠正用户，也不隐藏建议**。

## 验收对比

| 项 | 改前 | 改后 | 判过标准 |
|---|---|---|---|
| 报告第一行 swap 警戒 | 10240MB | 16384MB | **逐字变化**，不是"大概生效了" |
| 其余参数 | 20 / 7（报告显示 7+7 天）/ 未设 | 20 / 7（7+7 天）/ 未设 | 保持不变（只改目标键） |
| 第三行档位建议 | 10240MB 一致 | 10240MB（当前 16384MB），可下调 | 建议仍按内存档位算 |
| 提示行 | 无 | 无 | 若出现"超出范围，回退预设"，说明改的值越界了 |
| config 文件 | 备份在 | 目标键已改 | 用 `jq . config.json` 复核语法 |

## 常见错法

| 错法 | 后果 |
|---|---|
| 把 `16384` 写成 `"16GB"` | 类型不符 → 回退预设 + 提示；报告第一行仍是 10240 |
| 把天数写成 `0` | 越界（3~30）→ 回退；**`0` 不是"立刻删"**，本技能不支持零后悔期 |
| 手工编辑时多一个逗号 | 整份 config 判损坏 → 四项全部回退预设 |
| 改完只看文件不看报告 | 可能改在了另一份 config 上（`MC_CONFIG` 指向别处时的典型事故） |

## 什么时候该调

- **换机器**（16GB → 32GB）：按档位表调 swap 线，别沿用旧值。
- **换用法**（微信从常开变成偶尔开）：微信上限从 20 降到 12。
- **不要因为"看着数字高"就调**：`swap_warn_mb` 是"该动手了"的报警线，不是"swap 不该超过这个数"的硬指标。调高它等于**把报警推迟**，不改变 swap 本身（FAQ Q2）。

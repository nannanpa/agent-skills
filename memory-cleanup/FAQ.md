# FAQ

四问按"最容易被问错"的顺序排；第五问起是可复用模式，不绑定具体产品。

---

## Q1 为什么不能"看谁占内存大就杀谁"？

因为**占用大小不是状态指标**。RSS 回答"用了多少内存"，不回答"退掉会不会丢东西"。而占用大与"状态重"通常**正相关**：微信占内存多，是因为消息缓存、会话、未发送草稿都在里面；办公文档占内存多，是因为整份文档和撤销历史在内存里；浏览器占内存多，是因为几十个标签与登录会话。

所以"按大小排序杀"的结果**恰好等于"优先杀掉状态最重的进程"**——不是偶尔误伤，是系统性误伤，方向稳定地反了。

更关键的一层：macOS 的内存管理会优先回收可回收页（文件缓存、干净页），真正把内存逼到 swap 的是**常驻且不可回收**的部分。杀一个状态重的进程确实能腾出内存，代价是那部分状态，**收益与代价不在同一维度，不能相减**。

**本技能的做法**：只做**只读计数**（微信类进程 N 个，上限 M），异常时提示用户，由用户点名。技能没有"用户此刻还需不需要它"的信息渠道，就不替用户做这个决定。

完整机制推导见 `reference/安全边界.md` 第二节。

## Q2 为什么 swap 只能靠重启清零？

三个机制事实叠在一起：

1. **swap 文件由系统内核的换页机制按需创建**（内存压力上来就新建一片）。它没有面向用户空间的"缩容"接口。
2. **已写出的 swap 文件不会被删除**。即使内存压力下去、页面被换回内存（此时 `swap 已用` 会回落，"总大小/文件数"不缩），那几片文件仍然占着盘、仍算在 swap 里。
3. **shutdown / boot 时才清理 swap**。重启是唯一"从零重建 swap"的时机。

**常见误解**：`sudo purge` 能清 swap——不能。`purge` 清的是文件缓存与部分可回收内存，不动 swap 文件。

**所以报告里要说清两件事**：本轮 swap 已用**可能不降**（清理没白做，只是 swap 不会当场缩），想真正清零只有重启；这条建议的价值不在于"立刻做"，而在于让用户知道**什么时候该做**。

## Q3 为什么回收站不用 `mtime` 判"删除时间"？

因为 `mtime` 是**内容最后修改时间**，与"什么时候被删"没有关系。

- 一个 2019 年改过、今天刚删的文件，`mtime` 还是 2019 年。按 `mtime` 判超龄，它会在被删的**当天**被永久删除，后悔期为零。
- `mv` 在同一卷内**不改任何时间戳**（只改目录项）。所以文件搬进归档区后 `mtime` 依然是旧的，"进归档区多久了"用 `mtime` 判必然错，错的方向是**提前删**。

**本技能的做法**：搬进归档区时放进以当天日期命名的文件夹（`~/.Trash.aged/2026-11-16/`）。**文件夹名就是删除时间的记录**，用户肉眼可核、可手工纠正。

第二段用 `find … -name "????-??-??" -mtime +N`，判的是**文件夹**。文件夹的 `mtime` 每次往里搬东西都会更新，因此不早于其名字里的日期；用它做粗筛只会**延后**删除，不会提前。

一句话：**判据取自"名字里写的日期"，`mtime` 只当"够不够天数"的保守筛子，两者是"与"的关系。**

完整推导见 `reference/安全边界.md` 第五节。

## Q4 为什么 agent 自动化浏览器的实例会越积越多、自己却不退？

因为**没有人在替它收尸**：

1. 自动化浏览器是由驱动脚本（driver）拉起的独立进程，**不是脚本的子进程依赖**。POSIX 里进程退出不会连带终止同组的其他进程；macOS 也没有"父进程死亡则子进程收到 SIGKILL"这种默认机制。
2. 驱动脚本**正常结束**时一般会自己关浏览器；但**异常结束**（超时被杀、报错退出、任务被中断、终端被关）时，关闭那一步就没执行，浏览器实例留着继续跑。
3. 每个实例是完整的 Chromium：主进程 + GPU/渲染/网络子进程，合计**数百 MB**。十几个实例累加，就把 16GB 机型逼到 swap 上涨、系统开始彩虹圈。

**结论**：这是**必然发生的残留**，不是偶发故障——所以需要定期清理机制，而不是指望脚本自己收拾干净。本技能的默认产物就是"把残留量说清楚"，动手终止只是可选的一步。

## 附：双通道（对话触发 ＋ 定时触发）可复用模式

同一个流程被两条通道调用时，下面七条是通用要求。它们是**从故障里长出来的**，不是设计洁癖。

### 1. 判据单一真源

两条通道**引用同一份判据**（同一份 SKILL.md / 同一份参数表），不各写一份。各写一份的结果是：改动只落一边，两条通道对同一台机器给出不同结论，用户不知道信谁。

### 2. 无人值守侧不得包含"需要确认"的动作

定时通道跑在用户不知情的时候，**问不了"现在有任务在跑吗"**。所以：

| 动作 | 对话通道（有人值守） | 定时通道（无人值守） |
|---|---|---|
| 只读巡检、出报告 | 可 | 可 |
| 回收站搬移（可回退） | 可 | 可（推荐） |
| **终止进程** | 确认后可 | **不做** |
| **最终删除归档** | 确认后可 | **不做**，只列出待删清单 |

判据不变，**能力范围按"能不能问"裁剪**——不是把同一个脚本原样塞进定时任务。

### 3. 定时侧 prompt 必须自包含

无人值守侧不加载技能（加载了也走不到"先问用户"那一步），所以 prompt 里要把判据、阈值、路径、报告格式写齐。**自包含 ≠ 复制一份判据**：写齐的是"本次要执行的那几步"，判据仍指回真源。

### 4. 改动双向同步，并留一条对账线索

改判据时两侧同时改；对账线索最省事的做法是**在两条通道的报告里打同一个版本号**（沿用技能当前的版本号，别自己另编一个）。两边的版本号不一致，说明有一侧没同步——这比"记得去改"可靠。

### 5. 两通道报告用同一张表

同格式才能对账：定时侧早上留下的一组数值，就是对话侧白天的**基线**。两套格式的表，差值算不出来。

### 6. 时间窗要挑，且要留空窗说明

定时侧挑用户不用机器的时段（例如清晨），并在文档里写明"该时段无任务冲突"这一前提——**前提变了，时间窗就得重挑**，而不是默默跑下去。

### 7. 结论冲突时以判据为准

两通道给出不同结论时，**不回"哪次更新"，回"判据怎么写的"**。若判据本身有歧义，先修判据，再各自重跑。把冲突当"谁记得更牢"来解，下一次还会冲突。
